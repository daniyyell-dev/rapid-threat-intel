Behaviours are leads, not confirmed indicators, and can match legitimate activity. Compare any hit against your own baseline and environment before acting.

  1. 1

    alert hid.dll written to or loaded from the ink folder

    Look forhid.dll written to, or loaded from, C:\Program Files\Common Files\microsoft shared\ink\ (the DLL SignDrop plants through the SYSTEM .cnpf write)

    Why it mattersSignDrop redirects the CLFS .cnpf signature file, created as SYSTEM, to the ink folder as hid.dll, overwrites it with its payload and has consent.exe load it, then deletes it with a transacted delete. Windows does not ship hid.dll in the ink folder (the real one is in System32), so Cyderes rates any appearance there as alert-worthy whatever the variant. Tuning: matched on the exact file name and folder only. Expected false positives: none known; keep file and image-load telemetry for the ink folder because the file is removed after use.   2. 2

    alert consent.exe starting a console or shell

    Look forconsent.exe (the UAC consent UI) starting conhost.exe, cmd.exe, PowerShell or rundll32.exe

    Why it mattersCyderes found consent.exe, started as SYSTEM by the exploit's runas request, loads the planted hid.dll, whose payload opens a SYSTEM console on the user's desktop and kills the UAC prompt. consent.exe only draws the elevation prompt and does not start shells or consoles, so a child like this means code is running inside it. Summary

On 10 November 2026 the researcher behind the Nightmare-Eclipse releases (GitHub MSNightmare) published SignDrop, a working exploit that takes a standard user to SYSTEM on Windows with CLFS authentication active (Mode 0 or 1). It makes Microsoft Defender's signature-update RPC open a crafted CLFS log, so clfs.sys writes the .cnpf signature file as SYSTEM to a path chosen through Object Manager links, overwritten as C:\Program Files\Common Files\microsoft shared\ink\hid.dll and loaded by consent.exe. Cyderes reproduced a SYSTEM shell. There is no CVE or patch, and no in-the-wild use has been reported.

Note No attacker infrastructure or hashes exist; the path row is a host artefact for hunting, not something to block. Do not disable CLFS authentication as a workaround: it reopens the older memory-corruption bugs.

What to do

  1. Record HKLM\SYSTEM\CurrentControlSet\Services\CLFS\Authentication Mode on every host; Mode 0 or 1 is in scope.
  2. Alert on hid.dll created in or loaded from the ink folder and on consent.exe starting a console or shell.
  3. Tighten application and script control, since the exploit needs code running as a local user first.
  4. Apply Microsoft's fix when released; do not turn off CLFS authentication.
